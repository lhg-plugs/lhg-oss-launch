# lhg-ol-readme：README 编写

> **诚实声明**：本 skill 不编造数据；徽章只在有真实 CI/版本时加；演示材料必须为当前版本真实截图。

## 1. 何时使用

- 已有 `launch-brief.json`（见 lhg-ol-info），需要新写或改写 README 时。
- 收到一份 README，想按"发布标准"改写时——用第 4 节清单逐项打勾。
- `/lhg-oss-launch:oss-readme` 命令全程按本 skill 执行。

**不适用**：内部项目文档、私有库说明——本 skill 按"公开冷启动"标准写，内部文档不需要演示与传播设计。

## 2. 输入输出

### 输入
- `launch-brief.json`（one_liner 必须已确认）
- 目标语言（zh 缺省 / en）

### 输出
- `README.md`（可直接发布）
- 配套：LICENSE 文件检查结论、topics 关键词建议

## 3. 分步方法论：README 七段式

### 第 1 段：H1 标题
- 项目名，可加一句话副标题。不堆徽章：徽章 ≤3 个，且每个都有真实来源（CI 状态/版本号/许可证）。

### 第 2 段：GEO 答案块（核心中的核心）
```markdown
> 一句话介绍：给的，解决。（≥10 字，plain 句）

```bash
一键安装命令
```
```
- 这一块是给"AI 搜索 + 30 秒访客"看的：没有它，README 首屏等于没有门面。
- 一句话介绍直接用 brief 里用户确认过的 one_liner，不许改写走样。

### 第 3 段：演示（转化率最高的一段）
- 顺序：GIF > 短视频 > 截图。有动效证据优先。
- 视频必须标注时长（如"（时长 1:32）"），让访客知道要投入多久。
- GIF 注明大小/时长（如"约 2MB，循环播放"）。
- 截图必须为当前版本；旧版 UI 截图冒充新版 = 一票否决。

### 第 4 段：功能列表
- 写"用户得到什么"，不写"实现用了什么技术"。
- 每条 ≤20 字，动词开头："一句话整理下载文件夹""自定义归档规则"。
- 条数 3~7 条，贪多等于没有重点。

### 第 5 段：安装
- 一键安装命令放代码块，可复制。分平台（macOS/Linux/Windows）用表格或分小节。
- 安装后验证命令（如 `supertool --version`）必须真实可跑。

### 第 6 段：用法/快速开始
- 3 个以内最高频用法的可复制命令，每个配一句话说明。
- 进阶用法链到 docs/，README 里不展开。

### 第 7 段：许可/贡献/路线图
- 许可：声明类型 + 链到 LICENSE 文件；类型必须与 LICENSE 文件内容一致。
- 贡献：一句话 + 链到 CONTRIBUTING（如有）。
- 路线图：3~5 条，让访客知道项目往哪走。
- topics 建议：3~5 个 GitHub topics 关键词，写在 README 末尾注释或单独小节。

## 4. 发布前检查清单（写完逐项打勾）

1. [] H1 后 8 行内有一句话介绍（≥10 字）+ 安装代码块？
2. [] 安装/用法/许可三个章节都在？
3. [] 演示材料为当前版本真实截图/GIF/视频？视频标了时长？
4. [] 徽章 ≤3 个且都有真实来源？无 example.com/your-username 占位？
5. [] 所有链接可点：无空链接、无坏链、无 localhost？
6. [] 相对路径链接（图片/文档）指向的文件都存在？
7. [] LICENSE 文件存在，类型与 README 声明一致？
8. [] 无编造数字（star/用户量/下载量/排名/性能）？
9. [] 有版本号声明？有 topics 建议？
10. [] 中文项目有英文一句话摘要（或反之）？

## 5. 反模式

1. **徽章墙**：首屏 8 个徽章，介绍一句话没有——访客不知道你是谁，徽章再多也没用。
2. **技术自嗨**：功能列表写"基于 Rust 异步运行时"——用户不关心，用户关心"快不快、好不好用"。
3. **安装迷宫**：安装要分 5 步、每步配前置条件——一键安装做不到就诚实写步骤，不许写"一键"但实际 5 步。
4. **演示失真**：用 mock 图、旧版截图、"概念视频"冒充真实演示。
5. **许可裸奔**：README 写 MIT，仓库里没有 LICENSE 文件——等于没声明。
6. **占位符发布**：example.com、your-username、TODO 随 README 一起发布。

## 6. 多语言策略

- 主语言按受众定：中文社区项目主中文、英文社区主英文。
- 非主语言至少给一句话摘要 + 安装命令，不许"只有中文，爱看不看"。
- 翻译不许机翻后不校对：术语表先定（如"归档"统一译 archive），再全文统一。

## 7. 改写旧 README 流程

拿到一份现成的 README，按以下顺序改写，比从零写更快：

### 步骤 1：先跑审计
用 `oss_launch_audit.py` 跑一遍，blocker 清单就是改写任务清单（缺章节/坏链/占位符）。

### 步骤 2：重写首屏
- 保留 H1，重写一句话介绍（用 brief 的 one_liner）。
- 一键安装命令提到 H1 下方；徽章精简到 ≤3 个。
- 旧 README 的"长篇大论式开头"（三段背景介绍）整体删除，背景压缩进"为什么做"一句话。

### 步骤 3：补演示
- 无演示材料 → 按 lhg-ol-info 第 5 节先收集证据，再补。
- 有旧截图 → 全部重截当前版本；删掉 mock 图。

### 步骤 4：章节对齐
按第 3 节七段式重排章节；多余章节（"架构设计""FAQ 20 条"）移到 docs/，README 留链接。

### 步骤 5：链接大扫除
- 空链接、坏链、example.com、your-username 全部处理。
- 相对路径图片逐个点一遍，确认存在。

### 保留项
- 原有的真实用户反馈（带署名）、真实的 benchmark 数据——这些是资产，原样保留。
- 原有的贡献者名单——改写不许删贡献者。
- 原有的安装命令如果真实可用，原样保留并前移到首屏。

## 8. 自检与反馈

### 质检门（README 输出自查）- [] 第 4 节 10 项清单是否全绿？
- [] 49 条审计规则中 README 类（OL-README）是否零 blocker？
- [] 用户是否已确认一句话价值主张？

### 标准冒烟用例
输入：launch-brief.json（one_liner 已确认，evidence 有 1 张真实截图，gaps 含"缺演示视频"）。
期望输出：README.md 含 GEO 答案块、截图演示（无视频章节、不硬编）、安装/用法/许可三章节、LICENSE 检查通过、topics 建议；gaps 中的"演示视频"未出现在 README 中。

### 一键反馈
发现结构问题，以 `[QC] lhg-ol-readme <一句话>` 为标题提交到 https://github.com/lhg-plugs/lhg-oss-launch/issues，正文写清"输入 brief → 实际 README → 期望 README"。
