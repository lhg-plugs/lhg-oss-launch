# lhg-ol-info：项目信息挖掘

> **诚实声明**：本 skill 不编造任何数据；证据不足的条目标注"待补充"，不许用"想当然"填补。

## 1. 何时使用

- 用户说"帮我把这个项目推出去""准备发个 Show HN"时，**先挖掘、再写素材**。
- 本 skill 输出的 `launch-brief.json` 是 `lhg-ol-readme` 与 `lhg-ol-assets` 的唯一输入源。
- 给别人的项目做发布咨询时，同样先跑本 skill 形成 brief，避免"你说我写"的扯皮。

**不适用**：项目本身还没跑通、README 都没有、连一句话都说不清"它是干嘛的"——先回去把项目做完，本 skill 不负责"无中生有"。

## 2. 输入输出

### 输入
- 项目目录（代码 + 现有文档），或用户的一句话介绍。

### 输出：launch-brief.json

```json
{
"one_liner": "一句话价值主张（给谁、解决什么）",
"audience": "目标用户画像（一句话）",
"pain": "它解决的痛点（用户原话风格）",
"differentiator": "与同类方案的区别（一句话）",
"why_now": "为什么是现在（技术/生态/时机）",
"install": "一键安装命令",
"evidence": ["真实截图/GIF/演示链接", "可复现的 benchmark 方法"],
"gaps": ["待补充：性能对比数据"],
"topics": ["cli", "productivity"]
}
```

字段规则：`evidence` 为空数组时允许，但 `gaps` 必须诚实列出缺什么；`one_liner` 必须经用户确认。

## 3. 分步方法论：挖掘六步法

### 步骤 1：读代码，找"它到底是干嘛的"
- 看入口文件、README（如有）、package.json/cargo.toml 的 description。
- 用一句话写出来，句式："给的，解决"。
- 写不出 → 说明项目定位不清，打回给用户："先想清楚一句话，再谈发布"。

### 步骤 2：定目标用户（越具体越好）
- 反模式："给所有开发者用"。必须具体到场景："每天被下载文件夹淹没的 Mac 用户"。
- 用户越具体，launch 文案的钩子越准。

### 步骤 3：挖痛点（用户原话风格）
- 痛点要写成用户会抱怨的样子："下载文件夹 3 个月没整理，找文件靠搜索"。
- 不许写成特性罗列："支持 20 种规则"不是痛点，是特性。

### 步骤 4：找差异化（一句话）
- 列出 2~3 个同类方案，一句话说清"我们不一样在哪"。
- 差异化必须是用户可感知的（更快/更简单/更便宜），不是"架构更优雅"。
- 找不到差异化 → 诚实写进 gaps，不许硬编"业界首个"。

### 步骤 5：回答"为什么是现在"
- 新技术/新生态/新痛点，任选其一。没有 → 写"无明确时机，靠产品本身说话"，不许编趋势。
- 这一步决定 HN/PH 帖子的"钩子"有没有时效性。

### 步骤 6：列证据与缺口
- 证据：真实截图、GIF、可复现的 benchmark 方法、有链接的真实用户反馈。
- 缺口（gaps）：缺性能对比、缺演示视频、缺英文文档——诚实列出，素材环节自动避开这些点。
- **铁律**：gaps 里的东西不许出现在 launch 素材里。

## 4. brief 质检清单

1. [] one_liner 是否 30 字内说清"给谁、解决什么"？
2. [] audience 是否具体到场景，而非"所有开发者"？
3. [] pain 是否为用户抱怨风格，而非特性罗列？
4. [] differentiator 是否用户可感知？
5. [] evidence 是否每条都真实存在（有文件/链接）？
6. [] gaps 是否诚实列出，无"想当然"填补？
7. [] 用户是否已确认 one_liner？

## 5. 证据收集实操

证据是 launch 素材的"弹药"，没有证据的卖点写出来就是空话。本节讲怎么低成本收集。

### 截图/GIF（1 小时搞定）
- 用系统自带录屏：Mac（Shift+Cmd+5）、Windows（Xbox Game Bar）、Linux（peek/flameshot）。
- GIF 录制只录"一句话操作 → 结果"这一段，≤15 秒，宽度 ≤800px，体积控制在 5MB 内。
- 截图前清理：关闭无关标签页、退出登录态的个人信息、用测试数据（不许出现真实用户数据）。

### benchmark（半天搞定）
- 只测"用户可感知的指标"：启动时间、处理 1000 个文件的耗时、内存占用。
- 方法必须可复现：写清硬件、系统版本、测试命令，贴到 README 或 docs/benchmark.md。
- 对比对象选"用户现在在用的方案"（如手动整理、竞品 A），不选"空气"。
- 跑 3 次取中位数；只报中位数，不报最好的一次。

### 用户反馈（长期积累）
- 发布前没有用户很正常：gaps 里诚实写"待补充"，素材里不出现"用户好评"。
- 内测反馈要署名（"内测用户 @xxx"），不许写"用户一致好评"。
- 负面反馈比正面更有用：HN 帖子主动写"已知问题"，评论区反而更友好。

### 证据清单模板
```markdown
- [ ] 主 GIF：`assets/demo.gif`（一句话操作 → 结果，≤15s）
- [ ] 截图 2 张：主界面 + 结果对比
- [ ] benchmark：`docs/benchmark.md`（方法可复现）
- [ ] 演示视频脚本：`launch/demo-script.md`（90 秒分镜）
```

### 证据分级
- S 级（发布必需）：主 GIF 或演示视频、真实安装命令。
- A 级（强烈建议）：benchmark 方法、2 张对比截图。
- B 级（有更好）：用户反馈（署名）、路线图。
- 低于 S 级不许定发布日；缺 A 级要在 gaps 里写清补齐时间。
- 定级由用户确认：把分级表念给用户听，缺的项当场决定"补还是砍"。
- 证据收集是持续工作：brief 定稿后，gaps 清单转成 TODO，指派到人、定死日期。

## 6. 反模式

1. **特性当痛点**："支持 20 种规则"——用户不关心你支持多少，只关心"我的下载文件夹终于干净了"。
2. **受众泛化**："给所有人用"——等于给没人用。
3. **差异化硬编**："业界首个 AI 驱动"——搜一下，十个里有九个都这么写。
4. **证据注水**：把 roadmap 上的功能写成已发布；把"计划支持"写成"支持"。
5. **跳过用户确认**：one_liner 没经用户确认就往下写，返工率 100%。

## 7. 自检与反馈

### 质检门（brief 输出自查）
- [] 第 4 节 7 项清单是否全绿？
- [] launch-brief.json 字段是否齐全（见第 2 节 schema）？
- [] 是否无编造数字（star/用户量/下载量）？

### 标准冒烟用例
输入：一个本地 CLI 项目目录（含 package.json、README 草稿、无演示材料）。
期望输出：launch-brief.json 含 one_liner（用户已确认）、audience（具体场景）、pain（抱怨风格）、gaps（含"待补充：演示 GIF/视频"）、evidence（仅列真实存在项）。

### 一键反馈
发现挖掘逻辑问题，以 `[QC] lhg-ol-info <一句话>` 为标题提交到 https://github.com/lhg-plugs/lhg-oss-launch/issues，正文写清"输入项目 → 实际 brief → 期望 brief"。
